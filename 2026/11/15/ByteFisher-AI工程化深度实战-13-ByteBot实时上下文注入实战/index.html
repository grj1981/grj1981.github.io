ByteFisher AI 工程化深度实战（十三）：ByteBot 实时上下文注入实战——时间与天气

发表于 2026-11-15 分类于 AI Waline：
前 12 篇收官后的第一篇实战补遗。ByteBot 此前没有实时感知能力，用户问"现在几点""今天天气"只能靠模型猜甚至编造，且 IP 定位常常不准。本篇用上下文注入（system prompt 实时信息段）+ 对话引导 + 浏览器定位三层方案：Intl 时区时间、IP 定位 + Open-Meteo 免费天气、预置城市表识别用户报出的城市并按 IP 记住 30 分钟、navigator.geolocation 浏览器坐标定位、懒加载关键词与短跟进触发、TTL 缓存、超时降级，并给出注入 vs 函数调用选型对比与完整测试验证。

第 12 篇是本系列收官篇，但这不代表 ByteBot 就此定型。上线后收到一个高频吐槽：问它”现在几点””今天天气怎么样”，它会一本正经地报一个过时甚至编造的时间天气——因为 ByteBot 的 system prompt 里没有任何实时信息，模型只能凭训练数据”猜”。

本篇作为实战补遗，记录我给 ByteBot 补上”实时上下文”能力的完整过程：方案选型（上下文注入 vs 函数调用）、核心实现（时间、IP 定位、城市识别与地理编码、浏览器坐标、缓存、降级）、对话引导与浏览器定位、懒加载优化、测试验证，以及后续升级路径。

一、痛点与目标

改造前 ByteBot 的 system prompt 结构（api/chat.js 的 buildAdaptiveSystemPrompt）：

  • 角色设定（ByteFisher 博客 AI 助手）
  • 意图分类 + 全局规则
  • 博客概况（文章数、小游戏、相册等）
  • 候选文章列表

全部是静态信息。模型回答”现在几点”时只能根据训练数据估算，回答”今天天气”时基本是编造——这对一个主打”程序员 + 钓鱼”人设的助手来说很伤体验（钓鱼佬最关心的就是天气气压）。

改造目标（优先级排序）：

  1. 时间：准确、不编造，用户无感
  2. 天气：能拿到真实数据，失败时如实说明而不是编造
  3. 定位准确：IP 定位可能不准（VPN、运营商 NAT、代理出口），要能给用户纠偏的手段
  4. 零回归：不影响现有流式链路，前端零改动
  5. 低成本：免费数据源、懒加载、缓存，不拖慢对话

二、方案选型：注入 vs 函数调用

实现”实时能力”有两条主流路线，我做了完整对比：

维度 方案 A：上下文注入 方案 B：函数调用（Tools）
原理 请求时服务端拉取信息，拼进 system prompt 注册 tools，模型按需调 API，结果回填后二次请求
实现成本 低，只动服务端组装逻辑 高，要处理 tool_calls 分片 + 二次调用
前端改动 零 需适配 SSE 流中的 tool_calls 事件
Token 开销 每次请求多几十 token 按需，几乎为零
时效性 请求时点快照，够用 可追问用户地点，更精确
失败兜底 缺失字段走”如实说明”规则 模型自己决定是否降级

最终选 方案 A，理由很工程化：ByteBot 的定位是博客助手，时间/天气属于”背景信息”而非”交互工具”，每次请求花几十 token 换”永远在线”的确定性，比函数调用的流式复杂度划算得多。函数调用留作后续 MCP 化升级（见文末）。

方案 A 落地后暴露了第二个问题：IP 定位可能不准——VPN、公司 NAT、4G/5G 运营商出口，都可能让 IP 归属地落在别的城市。所以我再加了两层定位：对话引导（用户报出所在城市就按城市取天气）和浏览器定位（用户授权后前端 navigator.geolocation 直接拿精确坐标）。最终定位优先级是：用户明确报的城市 → 浏览器坐标 → IP 记忆城市 → IP 兜底。这是”注入框架 + 城市识别 + 浏览器定位”的混合形态，也是本文真正的主角。

三、整体设计

关键设计决策：

  1. 天气懒加载：只有命中天气关键词、或会话里出现了城市、或短跟进问句（如”明天呢”），才取定位和天气
  2. 定位优先级：用户明确报的城市 > 浏览器坐标 > IP 记忆城市 > IP 兜底——显式意图永远最高
  3. 浏览器定位：用户授权后精确到米；未授权/拒绝/超时静默回退，坐标只在需要时随请求发送，不落库
  4. 对话引导优先：用户告知城市后直接按城市出天气，并把城市按 IP 记住 30 分钟，后续”明天呢”不再追问
  5. 时间恒定注入：时间在服务端本地生成，零外部依赖、零延迟
  6. IP 定位兜底：从未定位时用 X-Forwarded-For 定位，system prompt 标注”按 IP 定位，可能不准确”，并引导模型询问用户所在城市
  7. 三层兜底：天气获取失败 → 不注入天气行，只留时间；时间生成异常 → 整个实时段跳过，降级为改造前
  8. 隐私友好：所有定位数据仅存在于内存缓存，不落库、不记录日志

四、核心实现

4.1 时间：Intl 时区格式化（含一个坑）

新建 api/lib/context-info.js：

踩坑记录：第一版我用 formatToParts 后只按 part.type 取值拼接，结果输出 2026年819日——因为 zh-CN 下 month: 'long' 的”月”是 literal 部件（值为 8 + 字面量 月），day 同理。只取 type 会把”月/日”字面量丢掉。正解是直接拼接所有 part.value，保持 ICU 输出的原始顺序。

4.2 IP 解析与过滤

要点：取 X-Forwarded-For 第一段（最接近真实客户端）；剔除 ::1 和所有私有网段——本地预览时不会白打定位 API；IPv6 去掉 [] 与 % 接口后缀。

4.3 定位 + 天气（双免费源，无需 key）

  • ip-api.com：免费、无 key，返回城市 + 经纬度。硬限制 45 次/分，用 TTL 缓存缓解
  • Open-Meteo：免费、无 key，覆盖全球含中国，current 参数一次拿温度/湿度/天气码/风速/风向

weather_code 是 WMO 编码，映射成中文描述（0 晴 / 2 多云 / 61 小雨 / 95 雷阵雨…），风向转 8 方位（北/东北/东…），风速 km/h 转风力等级（蒲福风级近似表）。

4.4 懒加载：关键词触发

设计取舍：适合钓鱼 也会触发——钓鱼佬问这个，本质上就是想看天气，值得一次外部调用。而”现在几点””聊聊 Unity”这类问题完全不走网络。

懒加载还有一个关键补充：触发条件不止关键词。只要会话里出现过城市（说明话题已进入天气/位置），或者是一句短跟进（如”明天呢””后天呢”），也会触发——否则”明天呢”会被漏掉。

4.5 对话引导：城市识别与地理编码

这是本次改造的核心新增。定位优先级：会话城市 → 该 IP 记忆的城市 → IP 兜底。

① 城市识别：预置城市表 + includes 匹配

为什么用预置城市表而不是让模型抽取？三点：确定性（同样输入永远同样输出）、可测试（单元测试直接断言）、零 token 成本。includes 全名匹配误命中率极低（”我在成都””成都天气””杭州好玩吗”都正确命中）。表里收录直辖市 + 省会 + 计划单列市 + 主要地级市（含义乌、东阳这些钓鱼大省常见城市）。

② 城市天气：Open-Meteo 地理编码（同样免费无 key）

一次地理编码拿到经纬度后，直接复用 4.3 的 getWeatherByCoords，两个免费源（ip-api + Open-Meteo 全家桶）零密钥组合。

③ 城市记忆：按 IP 记 30 分钟

用户报一次城市后，同一 IP 的后续提问（”明天呢””后天呢”）直接命中缓存城市，不会再追问一遍——这是”对话引导”体验顺滑的关键。

④ 优先级汇总

  • 杭州天气怎么样 → 会话命中 → 杭州
  • 我在成都 → 会话命中 → 成都（模型会顺势带一句当地天气）
  • 明天呢 → 历史有杭州 → 短跟进触发 → 杭州
  • 推荐点Unity教程 → 无关键词、无会话城市、非短跟进 → 不触发（不浪费 token）

4.7 TTL 缓存与降级

  • 每次外部调用用 AbortController + 3s 超时，失败静默返回 null，绝不阻塞对话主流程
  • 四张内存缓存（IP 天气 / IP 城市 / 城市天气 / 坐标天气）均 30 分钟 TTL，超过 500 条淘汰最旧（Vercel 冷启动会丢，无所谓，本来就是加速项）
  • 降级路径全链可用：懒加载不触发 → 只注入时间；定位/天气失败 → 只注入时间；getContextInfo 整体再包一层 try/catch → 零回归

4.6 浏览器定位：前端坐标 + 后端坐标路径

前两层定位（会话城市、IP）都有局限：用户没报城市时，IP 在移动网络 / NAT 下可能偏差几百公里。终极方案是让用户自己授权定位——浏览器 navigator.geolocation 在授权后可精确到几十米。

前端 source/js/ai-assistant.js 的改动（约 40 行）：

三个细节：只在命中天气关键词时触发定位（不打扰普通聊天）；授权弹窗一次性，用户拒绝或超时后 locationDenied=true 本会话不再请求；坐标只在本次请求携带，前端不存储。

上线踩坑后迭代成显式按钮 + Permissions API：Chrome 对连续忽略 3 次的授权会进入一周”静默块”——再调 getCurrentPosition 也不弹框，只剩 IP 兜底，用户毫无感知。所以不再静默请求，而是先查 navigator.permissions.query({name:'geolocation'})：granted 静默取坐标；prompt 时插入一条带 “允许定位”按钮的机器人消息，点击（全新用户手势 + 明确意图）才真正请求，成功后用坐标重发当前问题；denied 则提示去地址栏权限图标处开启。另一个教训是静态资源缓存失效：ai-assistant.js 靠 body-end.swig 里硬编码的 aiVersion 加查询串做 cache-bust，改代码必须同步升版本号，否则浏览器/Cloudflare 在 max-age=14400 窗口内继续跑旧 JS——“部署成功但功能没上”九成是这个原因。

每一级都只在上一级失败后才尝试，且返回 locationType（coords / city / ip）供注入段决定天气行的标注文案。用户报过城市时坐标直接跳过——显式意图永远最高。

关键在信任边界与纠偏入口：坐标/城市标注让用户信任数据来源，”按 IP 定位，可能不准确”主动坦白局限并触发询问引导——用户回一句”我在杭州”，下一轮立刻切到杭州天气。天气缺失时该行变成”暂未获取到天气信息；用户若询问天气，请如实说明暂时无法获取，不要编造”。

六、线上效果

上线后几个典型交互的表现：

提问 改造前 改造后
现在几点了 编造/过时时间 精确到分钟（北京时间）
今天天气怎么样（未报城市） 编造”晴天 25℃” 浏览器坐标/城市/IP 兜底，按来源标注可信度
我在杭州 / 杭州天气 无依据 按城市出准确天气，30 分钟内记住
明天呢（报过杭州后） 无依据瞎猜 复用杭州，无需再问
明天适合钓鱼吗 无依据瞎猜 有真实温度/湿度/风作为判断依据

成本与延迟：时间注入零外部依赖、零延迟；天气首次 ~1.5-3s（坐标直查天气最快，地理编码或 IP 定位次之），命中缓存 0ms；且只有”问天气 / 会话含城市 / 短跟进”才触发。因为懒加载 + 四张 TTL 缓存，绝大多数对话请求完全无感，ip-api 45 次/分限速从未打满。

七、演进方向

  1. 函数调用（MCP 化）：把 get_context_info 做成真正的 function calling，模型按需调用、可追问用户地点，配合流式 tool_calls 处理——这也是第 09 篇 MCP Server 的天然落点
  2. 高德 IP 定位：免费 ip-api 对部分国内 IP 仍有偏差，可升级高德 IP 定位 API（个人认证 5000 次/天）作为 IP 兜底层，精度大幅提升且无需用户授权
  3. 多数据源可插拔：代码里做成 provider 抽象，需要精度时可换和风/心知（Vercel 环境变量注入 key）
  4. 更多实时信息：博客最近更新、评论区热帖、钓点当前潮汐/气压——同一套”上下文注入 + 懒加载 + 缓存 + 降级”框架直接复用

八、小结

这次改造最大的收获不是”能报天气了”，而是两个可复用的模式：把”实时信息”当一等公民注入 system prompt，用懒加载控制成本、用 TTL 缓存兜底限速、用超时降级保住核心对话；以及**”多层定位 + 引导式纠偏”**——浏览器坐标 / 用户报的城市 / IP 记忆 / IP 兜底四级级联，模型主动坦白”按 IP 定位可能不准”并询问用户，把定位的主动权交还给最清楚自己位置的人。这也是 ByteBot 从”静态知识问答”走向”实时感知助手”的第一步——第 12 篇的 ByteBot v2 架构图上，又多了一个”实时上下文层”。
