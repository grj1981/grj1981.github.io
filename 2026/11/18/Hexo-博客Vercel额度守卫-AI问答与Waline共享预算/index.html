Hexo 博客 Vercel 额度守卫：AI 问答与 Waline 的共享预算实战

发表于 2026-11-18 分类于 博客实战 Waline：
Vercel Hobby 的 4 小时 Active CPU 额度被 AI 问答、Waline 评论和访问统计共同消耗，额度告警邮件越来越频繁。本文记录从批量上报、懒加载评论到 TiDB 共享预算守卫的完整过程：一条原子 UPDATE 如何同时管住两个 Vercel 项目，以及上线时踩到的 Waline ESM 坑。

前言：告警邮件一封接一封

后台的 Active CPU 用量停在 3 小时 44 分，距离 Hobby 的 4 小时额度只剩 16 分钟。那几天 Vercel 的额度告警邮件一封接一封，但项目还没有被 pause。

没有 pause 不代表安全。按 Vercel 文档，Hobby 超出 Fluid Compute 额度后，生产部署可能进入 503 DEPLOYMENT_PAUSED，而且不会自己恢复；要么等 30 天，要么联系支持或升级 Pro。对一个静态博客来说，这个代价太高了。

ByteFisher 博客主体是 Hexo 生成的静态页面，但仍有三个动态入口在跑 Vercel Functions：

  • ByteBot：AI 问答，流式调用 DeepSeek。
  • Waline：评论、文章阅读计数。
  • 访问统计：站点 PV/UV 上报。

更关键的是，ByteBot 和 Waline 是两个独立的 Vercel 项目，却挂在同一个 Hobby 账号下。Vercel 的免费额度是团队级的，两个项目共享同一个 4 小时。告警邮件只会告诉你“总量快超了”，不会告诉你“是聊天、评论还是统计用掉的”。

既然算不清谁用的，就做总账。

一、先算账：4 小时到底是什么

Vercel Hobby 的 Fluid Compute 额度主要看三项：

资源 Hobby 额度 我们当时的情况
Active CPU 4 小时/月 3 小时 44 分，接近红线
Invocations 100 万/月 远未到
Provisioned Memory 360 GB-hrs/月 未单独细算

真正先撞线的是 Active CPU，不是调用次数。

Active CPU 只在你自己的代码真正执行时计费。等 DeepSeek 返回、等 TiDB 查询、等网络 I/O 的时间不算 CPU；但函数实例的内存仍然按存活时间计费。所以一个“等模型回答”的聊天请求，CPU 可能不高，但内存会持续占用；而 Waline 的评论列表、统计写入这类请求，单次 CPU 反而更密集。

这也意味着：不能简单假设“AI 问答是唯一元凶”。聊天、评论、统计都在同一个池子里，告警邮件又不按功能拆分，唯一稳妥的办法是给整个池子加一个总预算，再把各功能的用量记录下来。

二、止血：先把函数调用降下来

在加预算之前，先做了一轮“降调用”。预算守卫是最后一道闸门，但如果请求本身能少发，闸门压力会小很多。

2.1 访问统计：从每页一次改成批量上报

原来的统计脚本每打开一个页面就发一次事件请求。现在改成批量队列：

  • 攒够 5 条立即发；
  • 不够 5 条，15 秒后发；
  • 单批最多 20 条；
  • 页面隐藏或离开时用 sendBeacon 兜底；
  • 前端统计快照刷新间隔从 10 分钟放宽到 30 分钟。

服务端 api/site-stats-event.js 相应支持 views[] 数组，并在一个事务里批量写入。这样同样的访问量，函数调用次数和 Active CPU 都会下降。

2.2 Waline：列表页不再请求计数

以前列表页、归档页也会加载 Waline，并请求文章计数。现在只有文章页和留言页才初始化评论：

  • 列表页直接跳过 Waline 脚本；
  • 文章页只发一次阅读计数 POST；
  • 评论脚本通过 NexT.utils.loadComments 延迟到评论区进入视口再加载；
  • 阅读计数只更新当前文章，不再重复请求。

这一轮改动在 themes/next/layout/_third-party/comments/waline.swig 里，效果很直接：列表页不再产生 Waline 函数调用，文章页的请求次数也可控了。

2.3 Chat：先校验，再决定是否进入重逻辑

api/chat.js 在调用 DeepSeek 之前会做这些检查：

  • Origin 是否来自博客域名；
  • 是否显式要求流式（stream: true）；
  • 消息数量、单条长度、总长度是否超限；
  • DeepSeek API Key 是否存在。

非法请求、非流式请求、跨域请求会在进入预算和上游调用之前被拒绝。这样攻击者不能靠一堆无效请求把额度烧光。

但优化只能降低斜率，不能给出上限。真正需要的是“今天最多用多少”的硬约束。

三、方案选型：为什么是共享预算表

3.1 先排除几个方案

per-IP 限流：能挡住单个 IP 的滥用，但挡不住分布式请求、代理池和 NAT 后的正常用户；而且 Vercel 额度是全局的，per-IP 限流不能保证总量不超。

Vercel WAF / Rate Limit：平台层能力更靠前，但 Hobby 计划的能力和配额有限，而且它按请求计数，不知道“聊天一次”和“计数一次”的成本差异。

Upstash Redis / Vercel KV：做限流很合适，但会引入新的服务和密钥；这个博客已经有 TiDB，单表原子更新足够，没必要再加一个组件。

升级 Pro：这是最彻底的方案，但对个人博客来说，先用免费额度把边界管好更划算。等访问量真的上来，再升级不迟。

3.2 选 TiDB 单表共享预算

最终方案是：在已有的 TiDB 里建一张 bytefisher_usage_budget，两个 Vercel 项目都读写同一张表。

  • 一天一行，记录当天总用量和分项用量；
  • 每次 API 请求先尝试“扣预算”；
  • 扣得动就放行，扣不动就返回 429；
  • 数据库异常时 fail-open，不让预算系统成为新的故障点。

为什么是 6 分钟/天？

4 小时按 30 天平均是 8 分钟/天。直接吃满 8 分钟没有任何缓冲，任何一次构建、重试或异常都会把总量推过线。把预算定在 6 分钟/天（360000ms），30 天合计 3 小时，给 4 小时额度留出 1 小时缓冲。

这不是精确计费，而是一条政策线。权重可以按实际观测调整，但总量必须可控。

3.3 共享预算的取舍

共享预算保证“总账不超”，但也会带来一个副作用：如果 ByteBot 一天内被刷爆，Waline 评论也会一起被 429。

这是有意的取舍。免费额度是团队级的，如果两个项目各自为政，最后一定是总量超标。表里保留 chat_ms 和 waline_ms 两列，先做可见性；以后如果确实需要，可以在 consume 里加功能级上限。

另外，BUDGET_ENFORCE=false 可以进入观察模式：只记录、不拦截。更稳妥的上线方式是先观察 3 天，确认权重和实际用量接近，再打开强制。这次因为额度只剩 16 分钟，直接开了强制。

四、数据模型：一天一行

几个设计点：

  • 不做每请求日志。每次请求写一行会把小表变成大表，增加 TiDB 写入和查询成本；预算只需要当天聚合值。
  • 按天一行。主键就是日期，更新和查询都只命中一行，锁冲突很小。
  • 分项列。chat_ms 和 waline_ms 用来观察各功能占比；requests 用来判断请求量级。
  • 自动建表。每个函数实例第一次用到时执行 CREATE TABLE IF NOT EXISTS，用 schemaPromise 避免并发重复 DDL；失败后 5 分钟内不再重试，避免数据库故障时反复打 DDL。

六、接入 Chat：预算放在校验之后

api/chat.js 的处理顺序很重要：

  1. 设置 CORS 头；
  2. OPTIONS 直接返回 204；
  3. 只允许 POST；
  4. 校验 Origin；
  5. 要求 stream: true；
  6. 清洗消息（最多 12 条、单条 4000 字符、总长 12000）；
  7. 检查 DeepSeek API Key；
  8. 扣预算；
  9. 构建 RAG 上下文；
  10. 调用 DeepSeek 并转发 SSE。

预算放在第 8 步，而不是最前面。原因很简单：非法请求、非流式请求、跨域请求不应该消耗额度。否则攻击者不需要真正用上 AI，只要不断发无效请求就能把预算打空。

CORS 不是鉴权。非浏览器客户端可以伪造 Origin，所以 Origin 校验只解决浏览器侧的体验问题，真正守住额度的是预算表。

八、测试：不要用生产额度试错

预算逻辑最怕两件事：并发下超扣、数据库故障时把业务打死。所以先写测试，再上线。

tests/usage-budget.test.js 用一个假 pool 模拟 SQL，覆盖：

  • 额度内允许；
  • 超限拒绝并返回 retryAfter；
  • 数据库故障 fail-open；
  • 观察模式记录但不拦截；
  • CST 跨日边界；
  • 未知 kind 直接抛错，不拼 SQL。

tests/chat-budget.test.js 验证：

  • 429 时不会调用上游；
  • 非流式请求在扣预算之前被拒绝；
  • 生产环境非法 Origin 在扣预算之前被拒绝；
  • 缺少用户消息在扣预算之前被拒绝。

Waline 侧同样有分类、委托、OPTIONS 和非 API 请求不计费的测试。

结果：

  • BlogCode 全量测试 71/71；
  • Waline 预算相关测试 10/10；
  • 本地 Node 25 + 真实 TiDB：/api/comment 返回 200，预算表写入后恢复测试数据；
  • 生产 smoke test：非流式返回 400、非法 Origin 返回 403、GET 返回 405、OPTIONS 返回 204；Waline 修复后根路径、/api/article、/api/comment 均返回 200。

九、上线插曲：Waline 的 ESM 雪崩

预算守卫上线时，Waline 项目先炸了一次。

项目初始部署在 2026 年 5 月 7 日，那时 @waline/vercel@latest 还是 1.39.3，依赖是 CommonJS。11 月 17 日重新部署时，latest 已经走到 1.43.4，依赖链变成了 ESM：

Waline 内部用 require() 加载 @mdit/plugin-emoji，但这个包在 1.43.4 里已经是纯 ESM。Vercel 的 Node 24 运行时没有像本地 Node 那样接受 require(ESM)，函数在启动阶段就崩了，所有请求返回 FUNCTION_INVOCATION_FAILED。

尝试过：

  • 设置 NODE_OPTIONS=--experimental-require-module；
  • 设置 VERCEL_USE_BYTECODE_CACHING=0；
  • 多次 Dashboard Redeploy。

仍然 500。链式 Redeploy 是否真正应用了运行时参数、旧字节码是否被复用，很难确认。与其继续赌运行时 flag，不如直接回到已知可用的依赖形态。

最后把 @waline/vercel 固定到 1.40.3：

  • 1.40.3 是最后一个全 CJS 依赖的版本；
  • 它使用 @mdit/plugin-sub/sup/katex/mathjax 的 *-cjs.0 版本；
  • emoji 走 markdown-it-emoji，没有 ESM 的 @mdit/plugin-emoji；
  • 它自带 jsdom ^19，所以移除了之前为 1.43.4 加的 jsdom override。

重新生成 lockfile、提交、触发一次全新的 Git 部署后，Waline 恢复 200。1.41.x 之后仍然使用 ESM 版 @mdit，1.43.7 也一样，所以这不是“升级到最新”能解决的问题。

这次踩坑的教训：

  • 平台显示的 Node 版本号，不等于完整的 Node 行为；
  • CJS 老项目升级依赖，要验证 require(ESM)，不能只看本地 node -v；
  • Dashboard Redeploy 不等于全新构建，必要时用新的 Git 提交触发部署；
  • 对关键服务，精确锁版本比 latest 可靠。

十、结果与反思

预算守卫上线后，最直接的变化不是“用户被限制了”，而是“额度终于可解释了”。

  • 6 分钟/天，30 天合计 3 小时，相对 4 小时留出 1 小时缓冲；
  • 聊天、评论、统计共享一张表，不会再出现“每个项目都以为自己还有 4 小时”；
  • 429 有明确文案和 Retry-After，用户知道什么时候再来；
  • 预算表里的 chat_ms / waline_ms 能看出功能占比，后续可以按真实数据调权重；
  • 告警邮件不再是唯一信号，每天的表就是一条可读的用量曲线。

做对的地方：

  • 用原子 UPDATE 而不是“先查再改”，并发下不会超扣；
  • 先校验再扣费，非法请求不能烧预算；
  • 数据库故障 fail-open，预算系统不成为新的单点；
  • 两个项目共享预算，符合 Vercel 团队级额度的现实；
  • 预算逻辑有单测，关键路径可以回归。

还能改进的地方：

  • 上线前先跑 3 天观察模式，确认权重和真实 Active CPU 的偏差；
  • 加 per-IP 令牌桶，先挡单点滥用，再让全局预算兜底；
  • 用量到 80% 时主动告警，而不是等 Vercel 发邮件；
  • 用 Vercel 后台的实际用量校准权重，而不是长期凭经验；
  • 如果访问量继续增长，Pro 或把统计迁到 Cloudflare Worker 都是选项。

免费额度不是无限的，但可以变成可预期的。预算守卫的价值，不是让用户少用，而是把“不可控的账单告警”变成一张每天能读懂的表格。
